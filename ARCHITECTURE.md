# VoIP: что нужно, чтобы звонки заработали

Короткий вывод: голосовой звонок — это не «микрофон + сокет». Это три независимых слоя, которые должны сойтись одновременно:

1. **Сигнализация** — кто кого вызывает, кто ответил, кто положил трубку.
2. **Медиа** — закодированный звук (и опционально видео) по RTP/SRTP.
3. **NAT traversal** — как два клиента за роутерами находят друг друга.

Без любого из трёх слоёв звонок либо не устанавливается, либо устанавливается, но тишина.

Ниже — минимальный набор, развилки стека и что сознательно **не** брать в MVP.

---

## 1. Что происходит в одном звонке

```
A                    Signaling                  B
|--- INVITE / offer --------------------------->|
|<-- 180 ringing / ringing --------------------|
|<-- 200 OK / answer --------------------------|
|--- ACK ------------------------------------->|

A  <======= ICE (STUN/TURN) + DTLS-SRTP ======>  B
A  <======= Opus audio frames (SRTP) =========>  B

A --- BYE / hangup ---------------------------->|
```

Пока клиенты не обменялись SDP (кодеки, ICE-кандидаты) и не пробили медиа-путь, звука не будет, даже если «вызов принят».

---

## 2. Обязательные компоненты

### 2.1 Идентичность и доступ

- Аккаунт: кто звонит, кому можно звонить.
- Аутентификация signalling-канала (JWT / session / SIP digest).
- Авторизация: whitelist, блок-лист, внутренние vs внешние номера.
- На мобильных — **push**, иначе входящий не дойдёт, пока приложение в фоне.

Без этого можно сделать демо «два браузера на одном экране». Нельзя сделать продукт.

### 2.2 Signaling-сервер

Задачи, которые нельзя отдать браузеру:

| Событие | Зачем сервер |
|---|---|
| Регистрация / presence | Знать, online ли абонент |
| Invite / ringing / answer / reject / hangup | Согласовать состояние вызова |
| Обмен SDP + ICE candidates | Связать медиа двух сторон |
| Таймауты | Неотвеченный вызов, обрыв сети |
| Маршрутизация | Найти устройство пользователя (web / iOS / Android) |

Протоколы:

- **WebRTC + свой signaling по WebSocket** — нормальный путь для своего приложения.
- **SIP (RFC 3261)** — если нужны софтфоны, ATC, PSTN-транки, интеграция с Asterisk/FreeSWITCH/Kamailio.
- **Готовый realtime-стек** (LiveKit, mediasoup, Janus) — если не хотим писать signaling и SFU сами.

Для 1:1 звонков в своём приложении достаточно своего signaling. SIP нужен, когда появляется АТС или городская телефония.

### 2.3 Медиа: кодек и транспорт

Минимальный аудио-путь:

- Захват микрофона → эхоподавление / AGC / noise suppression.
- Кодек: **Opus** (для IP это дефолт). G.711 — только ради PSTN.
- Пакеты: RTP, поверх — **SRTP** (шифрование).
- Контроль качества: RTCP (потери, jitter, RTT).

WebRTC закрывает захват, кодек, SRTP, jitter buffer и AEC из коробки. Свой RTP-стек писать не стоит.

Для 1:1 обычно хватает **P2P**. SFU (медиасервер) нужен когда:

- конференция на 3+ человек;
- запись звонка на сервере;
- один участник за жёстким NAT, и TURN дорого масштабировать;
- нужен PSTN-мост или транскодинг.

### 2.4 NAT: STUN и TURN

Большинство клиентов сидят за NAT. Нужны:

- **STUN** — узнать свой публичный адрес (дешёво, часто достаточно).
- **TURN** — реле медиа, когда P2P не пробивается (симметричный NAT, корпоративный firewall). Без TURN 10–30% звонков будут «соединилось, звука нет».
- **ICE** — клиенты пробуют host / srflx / relay кандидаты и выбирают рабочий путь.

Практичный сервер: **coturn**. Для продакшена — несколько точек рядом с пользователями: медиа не любит лишние 80 мс.

### 2.5 Клиенты

| Платформа | Что использовать | Что ещё нужно |
|---|---|---|
| Браузер | `RTCPeerConnection`, `getUserMedia` | Разрешение микрофона, страница в HTTPS |
| Android | WebRTC native / WebView | ConnectionService, foreground service, микрофон в фоне |
| iOS | WebRTC native | CallKit, VoIP push (PushKit), audio session |
| Десктоп | Electron + WebRTC или native SIP | Права на микрофон, поведение при сворачивании |

Входящий на телефоне — отдельная задача, не «ещё одна кнопка в UI».

### 2.6 Безопасность

- Signaling только по **TLS** (WSS / HTTPS / SIP over TLS).
- Медиа только **DTLS-SRTP**.
- Короткие токены на TURN (не общий секрет в клиенте).
- Rate limit на invite: иначе это бесплатная машина для спама и фрода.
- Согласие на запись, если запись вообще появится.

## 3. Чего нет в «просто звонке», но понадобится сразу после демо

| Тема | Зачем |
|---|---|
| Presence и устройства | Один пользователь — телефон + браузер |
| Reconnect / ICE restart | Wi‑Fi → LTE посреди разговора |
| Hold, mute, DTMF | Базовая телефония |
| История и missed calls | Ожидание продукта, не протокола |
| MOS / packet loss / jitter в метриках | Иначе «у меня не слышно» не диагностируется |
| Запись | Саппорт, комплаенс; нужна явная архитектура хранения |
| PSTN | Звонки на обычные номера: SIP-транк (Telnyx/Twilio) или Asterisk |
| Антифрод | Особенно если есть выход на городские номера |

## 4. Три реалистичных архитектуры

### A. Свой 1:1 WebRTC (рекомендуемый MVP)

```
[Client A] ──WSS──► [Signaling API] ◄──WSS── [Client B]
     │                     │                      │
     │              auth, rooms, SDP              │
     └──── SRTP (P2P) ─────┴────── или TURN ──────┘
                           │
                      [coturn]
```

Состав:

- клиент (web для проверки пути);
- signaling (WebSocket + состояние звонка);
- coturn;
- auth.

Плюс: полный контроль, мало движущихся частей.  
Минус: конференции, запись и PSTN потом придётся наращивать.

### B. SFU (LiveKit / mediasoup / Janus)

Нужен, если сразу закладываем группу, запись, симулькаст, серверную обработку. Signaling и медиа почти целиком чужие. Свой код — продукт вокруг: пользователи, комнаты, биллинг, UI.

### C. Классическая IP-телефония (SIP + АТС)

Kamailio/OpenSIPS (signaling) + RTPEngine + Asterisk/FreeSWITCH (IVR, очереди, транки). Имеет смысл, если цель — АТС, а не «звонки внутри приложения».

Смешивать A и C рано. WebRTC ↔ SIP мост (например, через Asterisk или Janus) — отдельный этап, когда появится PSTN.

## 5. MVP: что строим первым

Цель MVP — **два пользователя слышат друг друга**. Не конференция, не городские номера, не CallKit.

1. Аккаунт и логин.
2. Список контактов / room id (даже если руками).
3. Signaling: `invite`, `offer`, `answer`, `ice`, `hangup`, `reject`.
4. Web-клиент: кнопка «позвонить», индикатор ringing / in-call / ended.
5. Opus через WebRTC, STUN публичный + свой TURN.
6. Mute и hangup.
7. Логи: call-id, ICE state, выбранный кандидат (host/srflx/relay), bitrate, packet loss.

Критерий готовности: звонок проходит

- в одной сети;
- через разные NAT (дом ↔ мобильный интернет);
- после reload страницы состояние звонка корректно закрывается.

### Сознательно не в MVP

- видео;
- групповые звонки;
- PSTN;
- запись;
- SIP-софтфоны;
- нативный CallKit/ConnectionService;
- трансферы, очереди, IVR.

Иначе проект превращается в АТС до того, как заработает 1:1.

## 6. Предлагаемый стек для этого репозитория

Репозиторий пустой — стек ещё не зафиксирован. Рабочая ставка для своего продукта:

| Слой | Выбор | Почему |
|---|---|---|
| Клиент MVP | Web (TypeScript) | Быстрее всего проверить медиа |
| Signaling | Node.js / Go + WebSocket | Простой state machine звонка |
| Медиа | Browser WebRTC, P2P | Не писать RTP |
| NAT | coturn | Стандарт де-факто |
| Auth | JWT | Короткий путь до защищённого signaling |
| Дальше (не сейчас) | LiveKit или mediasoup | Когда появятся группы / запись |
| PSTN (не сейчас) | SIP trunk через провайдера | Не поднимать свою АТС ради одного транка |

Альтернатива, если цель — «чтобы за неделю были звонки, а не свой протокол»: LiveKit (open source + cloud). Тогда в этом репозитории остаётся продукт (пользователи, UI, политика комнат), а не медиастек.

## 7. Состояния звонка (минимум)

```
idle → calling → ringing → in_call → ended
                 ↘ rejected
                 ↘ missed
        calling → canceled
        in_call → failed   (ice failed / disconnect)
```

У каждой ноги (caller / callee) своё состояние, плюс общее `call_id`. Signaling должен переживать reconnect хотя бы на время установления. Медиа-reconnect (ICE restart) — сразу после того, как базовый путь стабилен.

---

## 8. Риски, которые обычно всплывают поздно

1. **«Сигнализация ок, медиа нет»** — нет TURN или ICE не доходит. Лечится coturn + логами кандидатов.
2. **Эхо и «робот»** — AEC не включён, плохой jitter, CPU. WebRTC помогает, но гарнитуры и мобильные всё равно надо слушать руками.
3. **Входящие на iOS/Android** — без VoIP push / CallKit звонок существует только пока приложение открыто.
4. **Стоимость TURN** — реле гоняет весь звук через ваш сервер. На объёме это основная статья.
5. **PSTN-фрод** — если открыть выход на телефонную сеть без жёстких лимитов, счёт провайдера улетает за ночь.
6. **Юрисдикция записи** — запись без явного UX и политики хранения нельзя «добавить потом незаметно».

## 9. Открытые решения (нужны до первой строки кода продукта)

1. **Свой signaling или LiveKit/аналог?** Свой — если 1:1 и контроль протокола важны. LiveKit — если быстрее нужен рабочий медиаслой.
2. **Только внутри приложения или ещё PSTN?** PSTN сразу тянет SIP, номера, биллинг, фрод.
3. **Только web или сразу мобильные?** Мобильный входящий — отдельный объём работы, сопоставимый с самим звонком.
4. **Только аудио или сразу видео?** Видео меняет TURN-счёт и заставляет думать про SFU раньше.
5. **Где пользователи?** TURN и SFU должны стоять близко к ним, иначе «как будто по рации».

Пока эти пять пунктов не закрыты, impl-план будет гадать. Для старта разумный дефолт:

> Web, 1:1 аудио, свой signaling, WebRTC P2P, coturn. Без PSTN, без групп, без нативных звонилок.

## 10. Порядок работ после согласования дефолта

1. Спека signaling-сообщений (`invite` / `offer` / `answer` / `ice` / `hangup`) и state machine.
2. Каркас auth + WebSocket-сервер.
3. Web-клиент с `RTCPeerConnection`.
4. coturn в окружении разработки.
5. Прогон NAT-сценариев и метрики ICE.
6. Только потом: второй клиент (mobile), presence, история, SFU/PSTN.

Этот документ — карта, не имплементация. Код имеет смысл начинать с пункта 1, когда дефолт из раздела 9 подтверждён.
